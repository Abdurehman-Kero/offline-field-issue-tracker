## 1. Problem Statement & Objectives
In infrastructure monitoring contexts (e.g., water points, rural energy facilities, civic maintenance, civil protection), field workers operate in environments with intermittent, low-bandwidth, or completely disconnected cellular connectivity. 

Standard web applications fail in such conditions, either dropping unsaved form data or producing duplicate submissions when reconnecting and retrying.

The **Offline Field Issue Tracker** solves this by providing:
1. **Offline-First Resilience**: All reporting actions occur against browser storage (IndexedDB) first; the UI never blocks waiting for network operations.
2. **Deterministic, Idempotent Synchronization**: Outbox items are tracked with client-generated UUIDs (`clientId`). Even with aggressive retries, zero duplicate records can be created on the central database.
3. **Strict Status Lifecycle**: A finite state machine governs valid status transitions based on simulated roles (`field_worker` vs. `coordinator`).
4. **Append-Only Audit History**: Every edit, status transition, duplicate flag, and synchronization attempt is immutably recorded for complete operational visibility.

---

## 2. Actors & Simulated Roles
Because external identity providers or password-based auth are omitted for this standalone assessment, roles are simulated via a global UI selector, transmitting `X-Role: field_worker | coordinator` with every API request.

- **Field Worker (`field_worker`)**:
  - Creates local drafts of infrastructure problems.
  - Edits or deletes draft reports on the local device.
  - Submits reports to the outbox for background synchronization.
  - Views reports and audit history.
- **Coordinator (`coordinator`)**:
  - Reviews synchronized reports.
  - Transitions report status (`Submitted -> Assigned -> In Progress -> Resolved / Rejected`).
  - Assigns reports to technicians or repair teams.
  - Corrects metadata (category, priority, description, location) prior to resolution or rejection.
  - Evaluates possible duplicate alerts.

## 3. Data Dictionary
- `id`: UUID (Primary Key, generated by server).
- `clientId`: UUID (Unique device-generated identifier, e.g. `crypto.randomUUID()`).
- `category`: Enum (`Water Point`, `Equipment Damage`, `Service Interruption`, `Safety Concern`, `Maintenance`, `Other`).
- `description`: String (10 to 1000 characters).
- `locationText`: String (3 to 200 characters).
- `latitude` / `longitude`: Decimal (-90 to 90 / -180 to 180). Both or neither must be provided.
- `priority`: Enum (`Low`, `Medium`, `High`, `Critical`), default `Medium`.
- `status`: Enum (`Draft`, `Submitted`, `Assigned`, `In Progress`, `Resolved`, `Rejected`).
- `reporterName`: String (2 to 80 characters).
- `assignedTo`: String or null (max 100 characters).
- `reportedAt`: ISO 8601 Timestamp (device capture time; cannot exceed 5 minutes in the future).
- `receivedAt`: ISO 8601 Timestamp (server receipt time).
- `updatedAt`: ISO 8601 Timestamp.
- `version`: Integer (starts at 1, incremented upon every coordinator modification).
- `possibleDuplicateOf`: UUID or null (reference to an earlier report).

## 4. Status Transition Matrix
| Current State | Target State | Authorized Actor | Required Fields / Payload |
|---|---|---|---|
| Draft | Submitted | field_worker | Valid required report fields |
| Submitted | Assigned | coordinator | `assignedTo` (non-empty string) |
| Submitted | Rejected | coordinator | `note` (justification) |
| Assigned | In Progress | coordinator | None |
| Assigned | Rejected | coordinator | `note` (justification) |
| In Progress | Resolved | coordinator | `note` (resolution summary) |
| In Progress | Assigned | coordinator | `assignedTo` (reassignment) |
| Resolved | In Progress | coordinator | `note` (reopen reason) |
| Rejected | None | None | Terminal state (cannot transition) |

Any other transition returns HTTP 422 `INVALID_TRANSITION`.
